# Удалить доступ (отвязка от компании / чата): полный план переноса в мобильное приложение

Документ описывает сценарий **`/delete`** и подтверждение **`/remove_access_comfirm`** из `server/telegram_dealer_bot` для переноса в `apk/POZ` + `server/mobile_app`.

**Смысл для бота:** отключить привязку Telegram-чата к компании в БД бота.  
**Смысл для POZ:** аналог — **отключить доступ пользователя к данным компании** в мобильном клиенте (отвязка аккаунта, выход, снятие устройства с учёта) по явному подтверждению, без изменения интеграции с 1С на стороне клиента.

## 2) Поток в Telegram (текущий)

### Шаг A — команда `/delete`

Вызывается `removeAccess(bot, chatId, userSessions, msg)` при **`awaitinRemoveAccess` ложно/не задано**:

- Отправляется вопрос: «Вы уверены что хотите удалить доступ к боту?»
- Кнопки: **Да** (`/remove_access_comfirm`), **Нет** (`/cancel`).

### Шаг B — callback `/remove_access_comfirm`

В `auth.js`:

1. Устанавливается `userSessions[chatId].awaitinRemoveAccess = true`.
2. Снова вызывается `removeAccess(...)`.
3. Внутри второго вызова:
   - по `chat_id` ищется `company_id` в **`user_company_tg_bot`**;
   - если найдено:
     - `UPDATE companies SET telegram_password = 'NOTACCES' WHERE id = company_id`;
     - `DELETE FROM user_company_tg_bot WHERE company_id = $1` (удаляются **все** строки с этим `company_id` в этой таблице);
     - `delete userSessions[chatId]`;
   - возвращается `{ success, message }`;
4. Пользователю отправляется `removalResult.message`.

**1С:** не вызывается.

**Важно для моделирования в POZ:** в боте удаление идёт по связке **чат ↔ компания** и затрагивает все записи `user_company_tg_bot` для данной компании — при проектировании мобильного аналога нужно явно решить, отвязываем ли **только текущего пользователя** или повторяем ту же бизнес-семантику (согласовать с заказчиком).

## 3) Перенос в `server/mobile_app`

| Задача | Рекомендация |
|--------|----------------|
| Эндпоинт | Например: `POST /mobile/account/revoke-access` после двухшагового UX в приложении (как подтверждение в боте). |
| Безопасность | Только авторизованный пользователь; проверка принадлежности к компании; идемпотентность повторного запроса. |
| Данные | Не доверять `companyId` из тела без сверки с сессией. |
| CRM / бот | Если учётные записи общие с `user_company_tg_bot`, согласовать единую политику отзыва доступа с бэкендом CRM. |

## 4) Паритет и тесты

- [ ] Двухшаговое подтверждение (ошибочные нажатия не отзывают доступ).
- [ ] Успех: пользователь не видит данные компании до повторной привязки/логина.
- [ ] Негатив: нет строки компании — понятное сообщение (как «Не удалось найти вашу компанию»).
- [ ] Регрессия: другие разделы приложения не ломаются после выхода.
