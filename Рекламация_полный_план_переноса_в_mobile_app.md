# Рекламация: полный план переноса в мобильное приложение

Документ фиксирует **всю логику рекламаций из `server/telegram_dealer_bot`** для полного переноса в `apk/POZ` + `server/mobile_app` без потери функционала.
Важно сохранять возможность использования мобильного приложения на android и IOS.
Важно учитывать логику авторизации, что данные должны попадать только тому кому они принадлежат, согласно авторизации.
Push-уведомления только там где они нужны: когда приходят от сервера ответы по рекламации.

## 2) Что входит в раздел "Рекламация" (полный охват)

В ТГ-боте раздел состоял из 3 пользовательских сценариев + 2 фоновых процесса:

1. **Сообщить о проблеме без оформления рекламации**
2. **Оформить новую рекламацию** (структурированно, пошагово)
3. **Информация о поданных рекламациях** (чтение из 1С)
4. **Фоновая обработка закрытых рекламаций** (cron, `V6Z`)
5. **Оценка закрытой рекламации + комментарий** (в БД и в 1С, `V0N...Q...`)

Для полного переноса в mobile_app нужно реализовать все 5 пунктов.

## 4) Сценарий A: "Сообщить о проблеме без оформления"

### Текущая логика (ТГ)

1. `handleComplaintReport` включает флаг:
   - `userSessions[chatId].awaitingComplaint = true`
2. `handleAwaitingComplaint` принимает:
   - текст (`msg.text`)
   - документы (`msg.document`)
   - фото (`msg.photo`)
   - подписи к файлам/фото (`msg.caption`)
3. Пользователь может отправить несколько сообщений и завершить кнопкой:
   - `finish_complaint_report`
4. Финал: `handleComplaintReportProblem`
   - собирает текст + ссылки на файлы/фото
   - определяет ответственного:
     - обычный режим: `getNokOrMppByCompany(companyId)`
     - если пришли из структурированной рекламации (см. ниже): `getMppByCompany(companyId)`
   - вызывает `createReminder(...)` с `typeReminders: 'complaint_report_problem'`

### Что обязательно перенести

- многократная отправка текст+вложения в рамках одной сессии
- подписи к вложениям
- явное завершение сессии
- надежная отправка задачи менеджеру с контекстом компании/пользователя

## 5) Сценарий B: "Оформить новую рекламацию" (главная сложность)

Это многошаговая state-машина. Ниже все этапы без пропусков.

### Этап 0. Выбор года + ввод номера заказа 1С

Флаг:
- `awaitingComplaintNewArrange = 0.5`, затем `1`

Поведение:
- по умолчанию год `2026`
- можно выбрать год кнопками (`2025/2024/2023/2022`)
- после выбора года пользователь вводит номер заказа

### Этап 1. Получение изделий заказа

Интеграция:
- `getOrderItemsAW(orderNo, companyInn, selectedYear)`

Если ничего не найдено:
- сообщение об ошибке
- выход из сценария (cancel/reset)

Если найдено:
- сохраняется список изделий:
  - `complaintDetailsAllItem = [NAME...]`
- переход к выбору изделия

### Этап 2. Выбор изделия

Флаг:
- `awaitingComplaintNewArrange = 2`

Поведение:
- пользователь выбирает изделие из кнопок
- в структуру добавляется:
  - `complaintDetails.push({ item, parts: [] })`
- переход к выбору объекта жалобы

### Этап 3. Выбор объекта жалобы

Флаг:
- `awaitingComplaintNewArrange = 3`

Объекты:
- Рама
- Створка
- Импост
- Заполнение
- Фурнитура
- Комплектующие
- Доставка

Структура:
- в выбранное изделие добавляется `part`:
  - `{ name: <объект>, reasons: [] }`

### Этап 4. Выбор недостатка (дефекта)

Флаг:
- `awaitingComplaintNewArrange = 4`

Недостатки зависят от объекта:

- Рама/Створка:
  - Лопина/скол
  - Царапина

- Импост:
  - Лопина/скол
  - Царапина
  - Щель

- Фурнитура:
  - Недовоз
  - Некомплект
  - Поломка

- Заполнение:
  - Бой/скол/лопина
  - Царапины/пузыри
  - Недовоз
  - Разгерметизация/Запотевание
  - Мусор/Герметик/Разводы
  - Раскладка/Фальш
  - Не соответствует формула

- Комплектующие:
  - Недовоз
  - Некомплект
  - Брак материала

- Доставка:
  - Опоздание
  - Персонал

Сохранение:
- выбранный недостаток добавляется в `part.reasons[]`

### Этап 5. Экран сводки и донабор данных

Флаг:
- `awaitingComplaintNewArrange = 5`

Пользователь видит сводку и может:
- `add_reason` -> добавить еще недостаток к текущему объекту
- `add_part` -> добавить новый объект жалобы в текущее изделие
- `add_item` -> добавить новое изделие
- `complaint_next` -> завершить конструктор и перейти к финальной отправке
- `cancel`

### Финал структурированной рекламации

При `complaint_next` вызывается `handleComplaintReport(...)` и далее `handleComplaintReportProblem(...)`.

В reminder уходит:
- произвольные тексты пользователя
- номер заказа
- вся структурированная часть (изделие -> объект -> недостатки)
- ссылки на вложения

## 6) Сценарий C: "Информация о поданных рекламациях"

### Текущая логика

- Формируется `sScan = V6R{companyInn}`
- Вызов: `sendRequest1C(sScan)`
- Ответ форматируется в читабельный список заявок со статусами

### Особенности формата (важно при переносе)

В `sendRequest1C` для `V6R` реализован спец-парсер:
- фильтрация служебных строк (`q11`, пустые)
- нормализация номера заявки/заказа
- whitelist статусов:
  - `В логистике`, `Устранено`, `Новая`, `В работе`, `Выполнено`, `Заказано`
- сбор комментария с учетом флагов `истина/ложь` и дат

Это нужно повторить максимально близко, иначе мобильный пользователь увидит "сырые" данные.

## 7) Фоновая часть, связанная с рекламацией (обязательно перенести)

## 7.1 Cron закрытых рекламаций (`V6Z`)

Источник:
- `helpers/api.js` -> `initReclamationCron`, `getReclamationClose`, `processReclamationResult`

Что делает:
1. По расписанию запрашивает 1С (`V6Z`)
2. Парсит закрытые рекламации
3. Сопоставляет компанию по ИНН/названию
4. Находит чат/пользователя
5. Отправляет карточку закрытия рекламации с кнопками рейтинга `1..5`
6. Сохраняет связку отправленного сообщения в БД

### Почему это критично

Без этого в mobile не будет полного цикла "обратной связи по качеству обработки рекламаций".

## 7.2 Оценка и комментарий

Источники:
- `handleReclamationRating`
- `handleRatingComment`
- `sendReclamationRating`

Поток:
1. Пользователь ставит рейтинг
2. Рейтинг сохраняется в БД (`reclamation_ratings`)
3. Пользователь может оставить комментарий
4. Рейтинг отправляется в 1С:
   - `V0N{claim}Q{rating}` (номер дополняется до 9 цифр)

## 15) Архитектурный стандарт для запросов в 1С (обязателен перед реализацией)

Чтобы не дублировать сокет-логику и не потерять контроль над форматами `Q11/Q12`, все запросы 1С в рекламации (и далее в других ветках) нужно строить через **единый шлюз 1С**.

### 15.1 Общий принцип

- Вынести общее подключение в один модуль:
  - `client.connect(8240, "192.168.57.77", ...)`
  - кодировка `windows-1251`
  - таймауты, ошибки, retry, закрытие сокета
- Ветки рекламации не должны напрямую работать с `net.Socket`.
- Клиент mobile не ходит в 1С напрямую, только через `server/mobile_app`.

### 15.2 Разделить ответственность на 4 слоя

1. `transport` (общее TCP взаимодействие)
- отправка/получение сырых данных;
- обработка timeout/error/disconnect;
- никаких бизнес-правил.

2. `messageBuilder` (сборка протокольных строк)
- формирует пакеты вида:
  - `Q11\x01EB35000999\x02\t${sScan}\r`
  - `Q12\x01EB35000999\x02\t${sScan}\r`
- учитывает опциональные аргументы (например, `date`).

3. `commandRegistry` (реестр команд)
- для каждой команды хранит:
  - как собрать `sScan` из аргументов;
  - какой протокол (`Q11` или `Q12`);
  - какой parser применить.

4. `parsers` (стратегии разбора ответа)
- отдельные парсеры для разных форматов:
  - `parseV6R` (рекламации со статусами),
  - `parseSimple` (V2R/V3R/V4R-подобные),
  - `parseAckQ12` (подтверждение отправки рейтинга),
  - и т.д.

### 15.3 Рекомендуемая структура в `server/mobile_app`

- `modules/shared/integrations/onec/transport.js`
- `modules/shared/integrations/onec/messageBuilder.js`
- `modules/shared/integrations/onec/commandRegistry.js`
- `modules/shared/integrations/onec/parsers/*.js`
- `modules/shared/integrations/onec/gateway.js`

### 15.4 Как вызывать из ветки "Рекламация"

Вместо прямых сокетов:
- `oneCGateway.execute("complaint.list", { inn })` -> аналог `V6R{inn}`
- `oneCGateway.execute("complaint.closed", {})` -> аналог `V6Z`
- `oneCGateway.execute("complaint.rating", { requestNumber, rating })` -> аналог `V0N...Q...` через `Q12`

### 15.5 Минимальный реестр команд для рекламации

- `complaint.list`
  - protocol: `Q11`
  - buildScan: `V6R${inn}`
  - parser: `parseV6R`

- `complaint.closed`
  - protocol: `Q11`
  - buildScan: `V6Z`
  - parser: `parseClosedClaims`

- `complaint.rating`
  - protocol: `Q12`
  - buildScan: `V0N${claimNumberPadded}Q${rating}`
  - parser: `parseAckQ12`

### 15.6 Почему это обязательно

- не будет копипаста `client.connect` в каждой ветке;
- проще поддерживать изменения протокола 1С;
- меньше риск сломать старую логику;
- легче тестировать (транспорт, builder, parser тестируются отдельно);
- ускоряет перенос остальных разделов (сверка, доставка, финансы), так как база уже готова.

### 15.7 Чеклист по внедрению стандарта

- [ ] В `mobile_app` создан единый `oneC` gateway
- [ ] Ветка рекламации не использует `net.Socket` напрямую
- [ ] Формирование `Q11/Q12` вынесено в `messageBuilder`
- [ ] Для `V6R`, `V6Z`, `V0N...Q...` есть отдельные parser-стратегии
- [ ] Ошибки/таймауты унифицированы и логируются в одном месте
- [ ] Контракты gateway покрыты тестами

## 16) Требование к архитектуре папок (обязательное)

Архитектура каталогов должна быть **упорядочена, понятна человеку и структурирована по веткам (feature-based)**, чтобы разработчик мог быстро находить нужную логику без "поиска по всему проекту".

### 16.1 Базовый принцип

- Группировать код **по бизнес-ветке**, а не по случайному набору технических папок.
- Для каждой ветки держать рядом:
  - контроллеры,
  - сервисы,
  - схемы/валидации,
  - мапперы/форматтеры,
  - тесты.
- Общие интеграции (`oneC`, `aw`, `reminder`, `push`) хранить в `shared`, без дублирования по веткам.

### 16.2 Рекомендуемый пример структуры (server/mobile_app)

```text
modules/
  complaints/
    controllers/
    services/
    flows/
    validators/
    mappers/
    tests/
  verification/
    controllers/
    services/
    validators/
    tests/
  delivery/
    controllers/
    services/
    validators/
    tests/
  finances/
    controllers/
    services/
    validators/
    tests/
  shared/
    integrations/
      onec/
      aw/
    reminders/
    notifications/
    utils/
```

### 16.3 Правила читаемости

- Названия папок и файлов отражают бизнес-смысл (`complaints`, `verification`, `delivery`).
- Один файл = одна ответственность (не собирать крупную разнородную логику в один файл).
- Не смешивать код разных веток в одном модуле.
- При добавлении новой ветки сначала определить ее место в структуре, затем писать код.

### 16.4 Что это дает проекту

- быстрый онбординг разработчика;
- предсказуемая навигация по коду;
- меньше регрессий при изменениях;
- проще масштабировать функционал мобильного приложения по новым веткам.



Оптимальный дизайн раздела “Рекламации”
1) Структура раздела
Сделать в разделе Еще -> Рекламации 3 вкладки:

Создать
Мои
Оценка
Это покрывает весь цикл из ТГ: создание, отслеживание, обратная связь.

2) Экран “Создать” (интуитивно)
Две крупные карточки:

Быстрое сообщение о проблеме
Оформить рекламацию по заказу
Пользователь сразу понимает разницу: быстро vs подробно.

3) “Оформить рекламацию” как пошаговый мастер
Лучший UX для сложной логики:

Шаг 1: Год + номер заказа
Шаг 2: Выбор изделия
Шаг 3: Объект жалобы
Шаг 4: Недостаток
Шаг 5: Комментарий + фото/файлы + отправка
Обязательно:

прогресс Шаг 2 из 5;
кнопки Назад/Далее;
автосохранение черновика;
итоговый экран “Проверить перед отправкой”.
4) “Мои рекламации”
Список карточек в стиле текущих новостей:

№ заявки
дата
кратко заказ/дефект
статус-бейдж (Новая, В работе, Устранено, Закрыта)
Открыть
В деталях карточки: таймлайн изменений + вложения + комментарии.

5) “Оценка”
Отдельный список закрытых рекламаций, где нужна оценка:

карточка + кнопки 1..5
после выбора: поле “Комментарий (необязательно)”
подтверждение отправки
Это очень удобно и визуально чисто.

Как сделать “красиво” в вашем стиле
сохранить ваш текущий визуальный язык: белые карточки, мягкие тени, спокойные отступы;
акцентным цветом выделять только действия (Отправить, Читать далее-аналог);
не перегружать иконками и текстом;
важное показывать статусами и чипами, а не длинными абзацами;
на каждом шаге одно основное действие.
Практические UX-правила для рекламации
один экран = одна задача;
минимум обязательных полей;
понятные тексты кнопок (“Добавить недостаток”, “Добавить изделие”);
безопасный выход с сохранением черновика;
после отправки — понятный результат и номер заявки.
