# План: сбор событий для аналитики и истории (Проекты, Задачи, Бизнес-процессы)

## Цель
Покрыть компоненты «Проекты», «Задачи» (канбан), «Бизнес-процессы» записью событий с датой, временем и пользователем для последующего анализа: время выполнения, этапы, просрочки, узкие места, статистика по отделам и сотрудникам.

---

## 1. Текущее состояние

### 1.1 Проекты (globalTask)
- **Таблица:** `global_task_history` (global_task_id, event_type, description, created_at, created_by, data JSONB).
- **Уже пишется:** создание проекта, смена статуса (Завершено, Пауза, Провал, Продолжить — через `updateGlobalTaskStatus`), создание/завершение подзадачи, добавление ответственных, согласование участника.
- **Не пишется:** удаление проекта (status = «Удален»), добавление документов к проекту, факт истечения дедлайна проекта.

### 1.2 Задачи (канбан, подзадачи)
- **Таблицы:** `tasks` (created_at, deadline, status, is_completed), `task_approvals`, `task_history` (task_id, changed_by, change_description, change_timestamp).
- **Сейчас:** в `task_history` по задачам (карточкам) записи не добавляются. Нет полей «когда исполнен» / «когда согласовано/отклонено» на уровне одной задачи.
- **Истечение дедлайна:** есть уведомления (taskDeadlineOverdue), отдельной таблицы/записи для аналитики нет.

### 1.3 Бизнес-процессы
- **Экземпляр:** `bp_process_instances` — есть `started_at`, `finished_at`.
- **Узлы:** `bp_node_execution_log` — есть `entered_at`, `exited_at`, `outcome`, т.е. время входа/выхода из блока уже фиксируется. Подходит для анализа «сколько времени в блоке» и узких мест.

## 2. Что нужно добавить

### 2.1 Проекты (globalTask)

| Действие | Куда писать | Что хранить |
|----------|-------------|-------------|
| Отметить выполненной / Пауза / Провал / Продолжить | Уже есть в `global_task_history` | — |
| **Удалить проект** (status = Удален) | `global_task_history` | event_type: «Удален» или «удаление», description, created_by, created_at |
| **Добавить подзадачу** | Уже есть («подзадача») | — |
| **Добавление документа** (файл к проекту) | `global_task_history` | event_type: «документ» / «добавление документа», description (имя файла или id вложения), created_by, created_at; в data — attachment_id, name_file при необходимости |
| **Истекший дедлайн проекта** | Вариант А: `global_task_history` с event_type «дедлайн истёк». Вариант Б: отдельная таблица `deadline_overdue_events` (entity_type, entity_id, deadline_at, detected_at, …) для гибкой аналитики | Дата дедлайна, дата фиксации (detected_at), при необходимости user_id (кто увидел/уведомлён) |

Рекомендация: минимум — писать в `global_task_history`; при появлении отчётов «все просрочки» удобно иметь отдельную таблицу событий просрочки (общую для проектов и задач).

### 2.2 Задачи (канбан, подзадачи)

Цель: иметь «дату/время создания и окончания», «дату установки в Выполнено исполнителем», «дату одобрения/отправки на доработку», «истекшие дедлайны».

| Что нужно | Решение |
|-----------|---------|
| Дата создания | Уже есть `tasks.created_at` |
| Дата окончания (фактическая) | Добавить в `tasks` поле `completed_at` (TIMESTAMP), заполнять при первом переходе `is_completed` в true |
| Дата «Выполнено исполнителем» | То же `completed_at` (или отдельное поле `marked_done_at` при желании различать) |
| Дата одобрения автором / отправки на доработку | Сейчас есть `task_approvals` (task_id, approver_id, is_approved), нет времени. Варианты: (1) добавить в `task_approvals` поля `approved_at`, `rejected_at` (или одно `responded_at` + тип); (2) или писать в `task_history` событие с change_timestamp. Для аналитики «среднее время согласования» удобнее колонки в `task_approvals` |
| Истекшие дедлайны задач | Аналогично проектам: либо запись в `task_history` (event «дедлайн истёк»), либо общая таблица `deadline_overdue_events` |
| История смены статуса / ключевых действий по задаче | Начать использовать `task_history`: при создании задачи, при установке is_completed = true, при одобрении/отклонении автором (если не храним только в task_approvals) |

Предлагаемый минимум:
- В БД: добавить `tasks.completed_at`; в `task_approvals` — `responded_at` (и при необходимости `approval_result`: approved/rejected).
- В коде: при установке задачи «выполнена» — обновлять `completed_at`; при согласовании/отклонении — обновлять `responded_at` в `task_approvals` и при необходимости писать в `task_history`; при создании задачи — одна запись в `task_history`.
- События «дедлайн истёк» — либо только в `task_history`, либо плюс общая таблица (см. ниже).

### 2.3 Бизнес-процессы

| Требование | Текущее состояние | Действия |
|------------|-------------------|----------|
| Дата/время начала и окончания | `bp_process_instances.started_at`, `finished_at` | Оставить как есть |

## 2.4 Данные для полной картины по бизнес-процессам (путь, время, узкие места)

Чтобы отслеживать весь путь экземпляра БП и точно определять, сколько что занимает времени и где узкие места, данные берутся из блоков «Задача» и «Проект» в БП.

### Структура БП: блоки и привязка данных к этапам

| Блок в БП | Как связывается с данными | Откуда берём статистику |
|-----------|---------------------------|--------------------------|
| **Создать проект** (create_project) | После создания проекта в register в контексте экземпляра пишется `context.project_outputs[node_id] = { global_task_id }`. **Имя этапа в отчёте** — это label узла из схемы (часто совпадает с названием проекта, напр. «Запрос поставщику»). | Раньше учитывались только узлы из `bp_gateway_project_waiting` (развилка «ожидание по проекту»), поэтому у узла «Создать проект» были нули. Теперь проекты подтягиваются и из **context.project_outputs**: по каждому node_id считаются проекты (автор, ответственные, согласование, документы, чат, время). |
| **Развилка по проекту** (gateway) | Когда процесс переходит в ожидание по проекту, в БД пишется `bp_gateway_project_waiting` (instance_id, **node_id развилки**, global_task_id). | Количество проектов, завершённые, ответственные, ожидание согласования, документы, время по проектам — из `bp_gateway_project_waiting` + `global_tasks` + `global_task_responsibles` + чат/история. |
| **Создать задачу** / **Задача** (create_task, assign_task) | При создании/привязке задачи пишется `bp_task_process_links` (task_id, process_instance_id, **node_id**). | Задачи по узлам: количество, с дедлайном, просрочено, авторы (tasks.created_by), исполнители (task_assignments), время от создания до завершения. |
| Подзадачи | Создаются как обычные tasks с parent_id; привязка к БП через родительскую задачу или через свою запись в bp_task_process_links (если подзадача создаётся блоком БП). | Сейчас считаются только задачи, явно попавшие в bp_task_process_links; при необходимости можно агрегировать по root_id. |

Итого: для этапа с названием «Запрос поставщику» (узел типа create_project) статистика по проекту (автор, ответственные, согласование, документы, время) берётся из **context.project_outputs** по этому node_id и из таблиц проектов (global_tasks, global_task_responsibles, task_attachments_global_tasks, global_task_chat_messages, global_task_history).

### Уже собирается и используется в аналитике

| Источник | Что даёт |
|----------|----------|
| `bp_process_instances` | started_at, finished_at, status; **context** (JSONB) — project_outputs для привязки проектов к узлу «Создать проект». |
| `bp_node_execution_log` | Эффективное время этапа (до следующей активности или до завершения), включая ожидания. |
| `bp_task_process_links` + `tasks` | Задачи по узлам: количество, выполнено, с дедлайном, просрочено, авторы, исполнители; время от создания до завершения. |
| `bp_gateway_project_waiting` + `global_tasks` | Проекты на **развилке** (ожидание по проекту): количество, завершено, прогресс, статусы, ответственные, ожидание согласования, документы, последняя активность (чат + история), время. |
| **context.project_outputs** (из bp_process_instances) | Проекты, **созданные в узле** «Создать проект»: (node_id → global_task_id). По ним подтягиваются те же данные, что и по gateway (автор проекта, ответственные, согласование, документы, время). |
| `bp_process_definitions.scheme` | Названия узлов (label) для подписей в отчётах. |
| **Почта по проекту** | `project_sent_emails` (message_id, global_task_id, user_id, sent_at) — кто и когда отправил письмо из карточки проекта. При получении ответа на письмо (createFinalSolutionFromEmailReply) в `project_email_response_times` пишется (sent_message_id, reply_received_at). Время ожидания ответа = reply_received_at − sent_at; учитывается для **автора письма** и его отдела. В деталях БП по узлам показывается пункт **«Почта»**: число раундов переписки (ответов) и суммарное время ожидания ответов; это время входит в суммарное время этапа и в расчёт узких мест. |

### Узкие места

Ранжирование этапов по **суммарному времени**: время этапа + время в задачах узла + время по проектам узла. Топ-3 этапа помечаются как узкие места. На клиенте в таблице «Детали по бизнес-процессам» выводятся: этап, проходы, время этапа, по задачам (кол-во, с дедлайном, просрочено, авторы, исполнители, время), по проектам (кол-во, завершено, ответственные, ожид. согласование, документы, время по проектам), узкое место.

### Кто тормозит: по участникам и отделам

Чтобы понимать, **кто из отделов и какой участник** больше всего затягивают выполнение (например, в процессе с проектом из 2 задач один сотрудник сделал быстро, другой — в два раза дольше), добавлены эндпоинты:

- **GET /api/analytics/bottlenecks/participants** — узкие места по исполнителям (assignee). Параметры: `scope` = `all` | `process` | `project` | `task`; при `process` — `processId`; при `project` — `globalTaskId`; при `task` — `rootTaskId` (задача и все подзадачи); `dateFrom`, `dateTo`; опционально `departmentId`. Возвращает по каждому участнику: отдел, кол-во задач, выполнено, среднее/суммарное время выполнения (сек), просрочено. Сортировка по суммарному времени (кто больше всего времени занял).
- **GET /api/analytics/bottlenecks/departments** — то же, сгруппировано по отделам.

**Сценарии:**
- **Бизнес-процесс с проектом и задачами:** выберите процесс в «Детали по бизнес-процессам» — блок «Кто тормозит выполнение» показывает участников и отделы по задачам этого процесса (`scope=process&processId=…`).
- **Проект не из БП:** вызвать `/api/analytics/bottlenecks/participants?scope=project&globalTaskId=<id проекта>&dateFrom=&dateTo=` (и аналогично departments) — получите, кто из исполнителей задач проекта дольше всего выполнял задачи.
- **Отдельная задача с подзадачами:** вызвать с `scope=task&rootTaskId=<id корневой задачи>` — учтутся все подзадачи дерева, видно, какой участник/отдел дольше всего.

Данные: задачи с привязкой к исполнителям (`task_assignments`), время = `completed_at - created_at` по выполненным задачам, просрочка = дедлайн прошёл, задача не завершена.

### Эндпоинт сущностей процесса

`GET /api/analytics/business-processes/:processId/entities?dateFrom=&dateTo=` возвращает список **задач** и **проектов** процесса с деталями:
- Задачи: node_id, instance_id, task_id, title, created_at, completed_at, deadline, overdue, author (id, name), assignees[].
- Проекты: node_id, instance_id, project_id, title, status, progress, created_at, deadline, author, responsiblesCount, approvalPending, docsCount, lastActivityAt (учёт чата и истории).

Это даёт полноценную картину для анализа: в какой момент что происходит дольше всего, кто задействован (исполнители, авторы, ответственные), где висят согласования и документы.

### Что пока не учитывается

| Данные | Комментарий |
|--------|-------------|
| Отправка описания проекта на почту / переписка по почте | Если переписка ведётся во внешней почте, для учёта нужны логи (например, сохранение факта отправки и ответов в БД). Чат проекта (global_task_chat_messages) уже учитывается в last_activity. |
| Кто действовал на шаге БП (ожидание пользователя, решение) | Для анализа «кто сколько времени тратил на шагах» — сохранять user_id в payload лога узла или в отдельном поле. |
| Подзадачи задач БП (агрегация по дереву) | Задачи из bp_task_process_links считаются по одной; подзадачи (parent_id) при желании можно агрегировать по root_id. |

### Компоненты «Проекты» и «Бизнес-процессы» — что откуда

- **Проекты (global_tasks):** created_at, deadline, status, progress; история в `global_task_history`; переписка в `global_task_chat_messages`; вложения в `task_attachments_global_tasks`; ответственные и согласование в `global_task_responsibles`. Всё это используется в аналитике БП для узлов с ожиданием проекта (`bp_gateway_project_waiting`).
- **БП:** экземпляры, лог узлов, задачи по узлам (с исполнителями, авторами, дедлайнами), проекты по узлам (с прогрессом, статусами, ответственными, документами, последней активностью). Узкие места считаются по суммарному времени (этап + задачи + проекты).

## 3. Единая таблица событий для гибкой аналитики (опционально)

Чтобы в будущем строить отчёты «по всем сущностям» и по отделам/сотрудникам без разбора нескольких таблиц, можно ввести одну таблицу событий:

```sql
-- Пример структуры (обсудить перед внедрением)
CREATE TABLE analytics_events (
  id SERIAL PRIMARY KEY,
  entity_type VARCHAR(30) NOT NULL,  -- 'global_task' | 'task' | 'bp_instance' | 'bp_node'
  entity_id INT NOT NULL,
  event_type VARCHAR(60) NOT NULL,  -- 'created' | 'status_completed' | 'status_paused' | 'deleted' | 'subtask_added' | 'document_added' | 'deadline_overdue' | 'task_completed' | 'task_approved' | 'task_rejected' | 'process_started' | 'process_finished' | 'node_entered' | 'node_exited' и т.д.
  occurred_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  user_id INT REFERENCES users(id) ON DELETE SET NULL,
  payload JSONB,  -- доп. данные (старый/новый статус, id подзадачи, id вложения, node_id, duration_seconds и т.д.)
  -- опционально: department_id, project_id (global_task_id), process_definition_id для быстрой фильтрации
);
CREATE INDEX idx_analytics_events_entity ON analytics_events(entity_type, entity_id);
CREATE INDEX idx_analytics_events_occurred ON analytics_events(occurred_at);
CREATE INDEX idx_analytics_events_user ON analytics_events(user_id);
CREATE INDEX idx_analytics_events_type ON analytics_events(event_type);
```

Тогда:
- существующую историю (global_task_history, task_history, bp_node_execution_log) можно оставить для UI «история изменений»;
- дублировать ключевые события в `analytics_events` для отчётов и дашбордов — единая точка для выборок по времени, пользователю, типу события, отделу.

Это можно сделать вторым этапом после того, как все нужные события будут гарантированно писаться в «свои» таблицы.

## 4. Просрочки и отчёты «здесь и сейчас»

Для выборок вида «все просроченные задачи/проекты на момент отчёта» достаточно опираться на текущие таблицы:
- `global_tasks.deadline`, `global_tasks.status`;
- `tasks.deadline`, `tasks.is_completed`, `tasks.status`.

Отдельная таблица `deadline_overdue_events` (entity_type, entity_id, deadline_at, detected_at, notified_user_ids и т.д.) имеет смысл, если нужна именно **история фактов просрочки** (когда впервые зафиксировали, кому отправили уведомление), а не только «сейчас просрочено».

## 5. Приоритеты реализации

### Фаза 1 — без новых таблиц (минимум для истории и базовой аналитики)

1. **Проекты**
   - При смене статуса на «Удален» — писать в `global_task_history` (event_type «удаление» / «Удален», created_by, created_at).
   - При добавлении вложения к проекту (task_attachments_global_tasks, tableType global) — писать в `global_task_history` (event_type «документ» или «добавление документа», description с именем файла, created_by).
   - Дедлайн проекта: при отправке уведомления/проверке «дедлайн истёк» — писать в `global_task_history` событие «дедлайн истёк» (created_at = момент фиксации, в data — deadline, при необходимости список уведомлённых).

2. **Задачи**
   - Добавить в БД: `tasks.completed_at` (TIMESTAMP NULL), в `task_approvals`: `responded_at` (TIMESTAMP NULL), при необходимости `approval_result` ('approved'|'rejected').
   - При установке is_completed = true — проставлять `tasks.completed_at` (один раз).
   - При одобрении/отклонении автором — обновлять `task_approvals.responded_at` (и approval_result).
   - Начать использовать `task_history`: при создании задачи — одна запись; при «выполнено исполнителем» и при одобрении/отклонении — запись с change_timestamp и changed_by.
   - Дедлайн задачи: при срабатывании «дедлайн истёк» (уведомление) — запись в `task_history` или в `global_task_history` (если хотим всё в проекте) с типом «дедлайн истёк» и ссылкой на task_id.

### Фаза 2 — при необходимости углублённой аналитики

3. **Таблица просрочек** (по желанию): `deadline_overdue_events` (entity_type, entity_id, deadline_at, detected_at, user_id и т.д.) и заполнять её при первой фиксации просрочки.
4. **Единая таблица событий** `analytics_events`: дублирование ключевых событий из global_task_history, task_history и при необходимости из bp_node_execution_log для единых отчётов по пользователям, отделам, периодам.
5. **БП:** при необходимости добавить в `bp_node_execution_log` или в payload поле «кто выполнил шаг» (user_id) для шагов с ожиданием пользователя.

## 6. Сводка по полям и местам в коде

| Проект: удаление | global_task_history | deleteGlobalTask (tasksController) — после UPDATE status = 'Удален' вызвать insertTaskHistory |
| Проект: документ | global_task_history | Обработчик добавления вложения (task_attachments_global_tasks при tableType global) — после INSERT вызвать insertTaskHistory |
| Проект: дедлайн истёк | global_task_history (или deadline_overdue_events) | Место, где формируется/отправляется уведомление о просрочке дедлайна проекта (если есть); иначе — отдельный job/проверка при открытии списка |
| Задача: completed_at | tasks.completed_at | Обработчик установки is_completed = true (approve/reject task) — при первом true проставить NOW() |
| Задача: responded_at | task_approvals.responded_at | Обработчик согласования/отклонения подзадачи автором — при обновлении approval проставить NOW() |
| Задача: история | task_history | createTask — INSERT; обработчик is_completed = true и обработчик approval — INSERT с change_description и changed_by |
| Задача: дедлайн истёк | task_history (или общая таблица) | Текущее место отправки уведомления taskDeadlineOverdue — добавить INSERT в task_history или в deadline_overdue_events |
