# Проектирование: Аналитика звонков, автоматизация задач и интеграция с бизнес-процессами

Документ для ознакомления и внесения корректировок перед реализацией.

---

## 1. Цели системы

1. **Аналитика**: понимать, кому когда звонили, по какому вопросу, сколько заказов сделал дилер/компания, сколько дней прошло с последнего заказа, когда «пора бы позвонить».
2. **Автоматизация**: по заданным параметрам создавать задачи или проекты с задачами (например, «Позвонить компании X»).
3. **Интеграция с БП**: возможность задействовать бизнес-процессы для отслеживания событий CRM (звонки, задачи, неизвестные номера).
4. **Неизвестные номера**: обработка входящих с номеров, которых нет в БД, — задача на добавление в систему.

---

## 2. Модель данных (как есть)

### 2.1. Основная единица — компания

- **companies** — базовая сущность (ИНН, название, статус, МПП, МПР, региональный менеджер и т.д.).
- **dealers** — сотрудники/контакты внутри компании (ФИО, должность, хобби).
- **dealer_phone_numbers** — телефоны дилеров (связаны с конкретным dealer_id).
- **phone_numbers_companies** — телефоны на уровне компании (общие номера).

### 2.2. Звонки

- **calls** — caller_number, receiver_number, accepted_at, status, purpose_id, description, outcome, reminder_id, task_id.
- Связь с дилером: `calls.caller_number` → `dealer_phone_numbers.phone_number` → `dealers` → `companies`.
- Связь с сотрудником: `calls.receiver_number` → `user_phones.phone_number` → `users`.

### 2.3. Заказы

- **orders_1c** — order_number, company_name, inn, shipping_date и др.
- Связь с компанией: `orders_1c.inn` = `companies.inn`.

### 2.4. Важные моменты

- Один номер может быть общим для компании (phone_numbers_companies) или личным для дилера (dealer_phone_numbers).
- Звонок «в компанию» может приходить на общий номер или на номер конкретного дилера.
- Для аналитики и автоматизации важно агрегировать данные на уровне **компании**, а не только дилера.

## 3. Аналитика

### 3.1. Что считать

| Метрика | Источник | Описание |
|--------|----------|----------|
| Последний звонок (входящий) | calls + dealer_phone_numbers + companies | Когда последний раз звонили с номера, связанного с компанией |
| Последний исходящий звонок | calls (receiver = номер компании/дилера) | Когда последний раз мы звонили в компанию |
| Последний звонок по цели | calls.purpose_id, call_purposes | По какому вопросу звонили (Расчёт, Консультация, Рекламация и т.д.) |
| Количество заказов | orders_1c по inn | Сколько заказов у компании за период |
| Дней с последнего заказа | orders_1c.shipping_date (MAX) | Сколько дней прошло с последней отгрузки |
| Дней без звонков | calls | Дней с последнего входящего или исходящего звонка |

### 3.2. Связь номера с компанией

Номер может относиться к компании через:

1. `dealer_phone_numbers` → `dealers` → `company_id`
2. `phone_numbers_companies` → `company_id`

При аналитике нужно учитывать оба источника.

### 3.3. Запрос данных по заказам (1С)

Сейчас `orders_1c` — локальная таблица. Для актуальных данных о последнем заказе потребуется:

- **Вариант A**: периодическая выгрузка из 1С в `orders_1c` (есть).
- **Вариант B**: API 1С (или аналогичной системы) для запроса «последний заказ по ИНН» в реальном времени.

Требуется уточнение: как часто обновляется `orders_1c` и нужен ли запрос в 1С по требованию.

## 4. Автоматическое создание задач

### 4.1. Условия (параметры)

Пользователь задаёт правила, например:

| Параметр | Описание | Пример |
|----------|----------|--------|
| Дней без входящего звонка | Компания не звонила нам N дней | 30 |
| Дней без исходящего звонка | Мы не звонили компании N дней | 14 |
| Дней с последнего заказа | Последний заказ был более N дней назад | 60 |
| Комбинации | Несколько условий через И/ИЛИ | (не звонили 14 дней) И (заказ был > 30 дней назад) |

### 4.2. Действие

При срабатывании правила:

- Создаётся **задача** (например, «Позвонить компании X», с указанием номера, МПП/МПР).
- Или создаётся **проект** с подзадачами (если логика сложнее).

### 4.3. Кому назначать

- По компании: `mpp_id`, `mpr_id`, `regional_manager_id` из `companies`.
- Или по настройкам правила: фиксированный исполнитель / роль / отдел.

### 4.4. Когда проверять

- **По расписанию** (cron): раз в день (или чаще) запускать проверку правил.
- **По событию**: после нового звонка или обновления заказов — пересчитывать метрики и правила (опционально).

## 5. Интеграция с бизнес-процессами (БП)

### 5.1. Текущие возможности БП

- Запуск по расписанию.
- Создание задач, проектов, уведомлений.
- Развилки по статусу задачи, проекту, инициатору, доп. информации.
- Ожидание: завершение задачи, таймер, принятие решения.

### 5.2. Чего не хватает

- **События из CRM**: звонок (входящий/исходящий), создание/закрытие задачи, входящий с неизвестного номера.
- **Условия по звонкам**: «звонок от компании X», «звонок с неизвестного номера», «N дней без звонка».

### 5.3. Варианты интеграции

**Вариант A. БП как подписчик событий CRM**

- CRM при событии (звонок, неизвестный номер) шлёт событие в BPE.
- BPE имеет блок «Событие CRM» (новый тип узла), который ждёт определённый тип события.
- При получении события процесс переходит к следующему узлу (создание задачи, уведомление и т.д.).

**Вариант B. Отдельный модуль в CRM**

- Модуль «Правила звонков» в CRM: условия + действия (создать задачу, создать проект).
- Не использует BPE, но проще внедрить.
- Ограниченная гибкость по сравнению с полными БП.

**Вариант C. Гибрид**

- Простые правила (условие → задача) — в CRM.
- Сложные сценарии (несколько шагов, согласования) — через БП, запускаемые из CRM по событию.

### 5.4. Рекомендация

- **Неизвестные номера** логичнее обрабатывать в CRM: при входящем звонке с номера, которого нет в `dealer_phone_numbers`, `user_phones`, `phone_numbers_companies` — сразу создавать задачу «Добавить номер в БД» или «Проверить контакт». Это не требует гибкости БП.
- **Периодическая аналитика** («пора позвонить») — cron + правила в CRM или отдельный воркер, который создаёт задачи.
- **БП** — для сложных сценариев: например, «при звонке от компании X после N дней без заказов → создать проект с задачей на звонок и задачей на проверку заказа».

## 6. Неизвестные номера

### 6.1. Где определять

- **Asterisk** (asterisk_server) при входящем звонке уже определяет caller.
- Если `findUserByPhoneNumber` и `findDealerByPhoneNumber` не находят номер, это «неизвестный».
- Нужно также проверять `phone_numbers_companies`.

### 6.2. Действия

1. **Уведомление** — показать в модальном окне «Неизвестный номер», с кнопкой «Добавить в контакты».
2. **Авто-задача** — создавать задачу «Проверить и добавить номер X в CRM» (по настройкам: всегда / никогда / по правилам).
3. **Событие в БП** (если выбран вариант A в п. 5.3) — передать событие «incoming_unknown_number» в BPE.

### 6.3. Рекомендация

Обрабатывать неизвестные номера в CRM: это быстрее внедрить и проще поддерживать. БП подключать только при необходимости сложных сценариев.

## 7. Что нужно добавить / изменить

### 7.1. База данных

| Изменение | Назначение |
|-----------|------------|
| Связь calls с company_id | Явная связь звонка с компанией (сейчас через номер → дилер → компания) |
| Таблица правил автоматизации | call_automation_rules: условия (дней без звонка, дней с заказа), действие (задача/проект), кому назначать |
| Расширение звонков | Направление: входящий/исходящий (если Asterisk отдаёт эту информацию) |
| Кэш/матчинг номеров с компанией | phone_numbers_companies + dealer_phone_numbers для быстрого поиска company_id по номеру |

### 7.2. Asterisk / телефония

- Различать входящие и исходящие (если ещё не различается).
- Событие «неизвестный номер» — отдельный тип или флаг в данных звонка.

### 7.3. Интеграция с 1С

- Способ получения «последний заказ по ИНН»: выгрузка, API, промежуточная БД.
- Периодичность обновления и формат данных.

### 7.4. Новые компоненты

- **Модуль аналитики звонков** — дашборд/отчёт: компании, последний звонок, последний заказ, «пора позвонить».
- **Настройки правил** — UI для создания/редактирования правил автоматизации.
- **Воркер проверки правил** — cron (например, раз в день) проверяет правила и создаёт задачи.
- **Обработка неизвестных номеров** — логика в asterisk_server/CRM при входящем с неизвестного номера.

### 7.5. Бизнес-процессы (опционально)

- Новый тип узла «Событие CRM» — ожидание внешнего события (звонок, неизвестный номер).
- API BPE для приёма событий от CRM.
- Условия развилки по типу события и параметрам звонка.

## 10. Вопросы для уточнения

1. Нужна ли аналитика по **сотрудникам** (кто кому звонил), или только по компаниям?
2. Учитывать ли **пропущенные** звонки в аналитике?
3. «Дней без заказа» — брать из `orders_1c` или из внешней системы в реальном времени?
