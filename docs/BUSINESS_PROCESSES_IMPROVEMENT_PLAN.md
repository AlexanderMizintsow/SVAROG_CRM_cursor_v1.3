# План усовершенствований бизнес-процессов

Документ описывает поэтапный план обновлений компонентов Business Processes и KanbanBoard в SVAROG CRM. Выполнять по запросу поэтапно.

## ФАЗА 1: Исправление критических недочётов (быстрые правки)

### 1.1. Backspace vs Delete при редактировании названия блока

**Проблема:** При вводе «Название блока на схеме» в PropertiesPanel при нажатии Backspace удаляется весь блок (или ничего не происходит), т.к. глобальный обработчик `keydown` в FlowCanvas реагирует и на Delete, и на Backspace.

**Решение:**
- **Клиент:** `FlowCanvas.jsx` — в обработчике `handleKeyDown`:
  1. Разрешить удаление блока **только по клавише Delete** (убрать реакцию на Backspace).
  2. Добавить проверку: если фокус в `input`, `textarea` или `select` (включая PropertiesPanel), **не** удалять блок — пользователь редактирует текст.

**Файлы:** `client/src/routes/businessProcesses/ProcessDesigner/Canvas/FlowCanvas.jsx`

---

### 1.2. Галочка «Разрешить запуск всем» в блоке СТАРТ

**Проблема:** После снятия галочки «Разрешить запуск всем» её невозможно снова установить.

**Причина:** В `StartNodeProps.jsx` при `onChange` вызываются два `handleChange` подряд: `handleChange('allowAllLaunchers', true)` и `handleChange('allowedLauncherUserIds', [])`. Второй вызов использует старый `settings` из замыкания и перезаписывает первый результат (allowAllLaunchers снова становится false или не сохраняется).

**Решение:**
- **Клиент:** `StartNodeProps.jsx` — при установке галочки вызывать **один** `onUpdate` с обоими полями:
  ```js
  onUpdate({ settings: { ...settings, allowAllLaunchers: true, allowedLauncherUserIds: [] } })
  ```

**Файлы:** `client/src/routes/businessProcesses/ProcessDesigner/PropertiesPanel/StartNodeProps.jsx`

### 1.3. Выбор пользователей галочками вместо выделения

  - Выбранные пользователи отображаются с галочкой.
- Использовать в:
  - `StartNodeProps.jsx` — «Кто может запускать процесс»
  - `CreateTaskNodeProps.jsx` — Исполнители, Утверждающие, Наблюдатели
  - `AssignTaskNodeProps.jsx` — Пользователи
  - `NotificationNodeProps.jsx` — Пользователи

**Файлы:**
- Новый: `client/src/routes/businessProcesses/ProcessDesigner/PropertiesPanel/UserCheckboxList.jsx` (и .scss)
- Обновить: `StartNodeProps.jsx`, `CreateTaskNodeProps.jsx`, `AssignTaskNodeProps.jsx`, `NotificationNodeProps.jsx`

## ФАЗА 2: Валидация и проверки перед публикацией

### 2.1. Обязательные поля блоков

**Проблема:** Можно опубликовать процесс с незаполненными обязательными полями.

**Решение:**
- Расширить `validateScheme` в `ProcessDesigner.jsx`:
  1. **Блок СОЗДАТЬ ЗАДАЧУ** (режим «создать задачу сразу по шаблону»):
     - Обязательно: Название задачи (шаблон), Описание (шаблон), Пользователи (исполнители) — в зависимости от assigneeSource: при `users` — `assigneeUserIds` не пустой; при department/role — соответствующий id задан.
  2. **Блок УВЕДОМЛЕНИЯ**:
     - Обязательно: хотя бы один канал (inApp или telegram), Текст сообщения, Пользователи (при recipientSource=users — userIds не пустой; при department/role — id задан).

- Показывать Toast с конкретным сообщением об ошибке (например: «Блок «Уведомление»: выберите хотя бы один канал»).

**Файлы:** `client/src/routes/businessProcesses/ProcessDesigner/ProcessDesigner.jsx`

### 2.2. Проверка связности блоков

**Проблема:** Можно опубликовать процесс с «висящими» блоками (без входящих связей).

**Решение:**
- В `validateScheme` добавить проверку: каждый блок (кроме `start`) должен иметь **хотя бы одну входящую** стрелку (edge с `target === node.id`).
- Если есть блок без входящих связей — вернуть сообщение: «Блок «…» не связан со схемой. У каждого блока (кроме Старт) должен быть хотя бы один вход.»

**Файлы:** `client/src/routes/businessProcesses/ProcessDesigner/ProcessDesigner.jsx`

### 3.2. Составные условия (И/ИЛИ) и время/дата

**Проблема:** Нужна возможность задавать несколько условий в совокупности: «в процессе И ожидание одобрения» или «в работе ИЛИ в ожидании ИЛИ …», а также условия по времени («выполнено И время < 18:00»).

**Решение:**
- Расширить модель условия для стрелки:

  - Новое поле `conditions` — массив:

  - Новое поле `timeConstraint` (опционально):

- **Клиент:** `GatewayNodeProps.jsx` — UI для:
  1. Режим «Одно условие» / «Несколько условий (И/ИЛИ)».
  2. При нескольких — список условий с выбором AND/OR.
  3. Опционально — ограничение по времени/дате.

- **Сервер:** `gateway.js` — логика вычисления:
  - Если задан `conditions` — вычислять по AND/OR.
  - Если задан `timeConstraint` — дополнительная проверка (сравнение текущего времени с value).

**Файлы:**

## ФАЗА 4: Блок «ПРИНЯТИЕ РЕШЕНИЯ»

### 4.1. Описание блока

Блок похож на УВЕДОМЛЕНИЕ, но:
- **Ожидает возврата решения (события)** от пользователя.

## ФАЗА 5: Документация и переписка в рамках БП (стратегия)

### 5.1. Проблема

Сотрудники используют почту для запросов документации, подтверждений, переписки. Нужно перенести это внутрь приложения, внутри запущенного бизнес-процесса.

### 5.2. Мировые практики

- **Запрос документации (Document Request):** в BPMN часто реализуется как User Task с подтипом «Request Document» — исполнитель запрашивает документ у участника, тот загружает/отправляет.
- **Подтверждение получения (Acknowledgment):** User Task с кнопкой «Подтверждаю получение».
- **Документ по шаблону:** Service Task или скрипт генерирует документ по шаблону с подстановкой переменных процесса.

### 5.3. Предлагаемая архитектура (концепт)

**Вариант A — расширение блока ПРИНЯТИЕ РЕШЕНИЯ:**
- Добавить тип кнопки «Запросить документ» — при нажатии открывается форма: выбор типа документа, кому запросить, срок.
- В контексте экземпляра сохранять «запросы документов» и «приложенные документы».

**Вариант B — отдельный блок «ЗАПРОС ДОКУМЕНТА»:**
- Блок указывает: кто запрашивает, у кого, какой тип документа, дедлайн.
- При наступлении — создаётся задача/уведомление «Предоставьте документ X».
- При загрузке документа — процесс продолжается.
- Подтверждение получения — отдельная кнопка или следующий блок.

**Вариант C — общая «Переписка/Документы» внутри экземпляра:**
- Для каждого экземпляра БП — вкладка «Документы» и «Сообщения».
- Любой участник может загрузить документ или написать сообщение.
- Блоки БП могут ссылаться на «ожидание документа» или «ожидание подтверждения» как условие.

### 5.4. Рекомендуемый поэтапный подход

1. **Сначала** — реализовать блок ПРИНЯТИЕ РЕШЕНИЯ (Фаза 4) — он даст механику «ожидание ответа пользователя».
2. **Затем** — добавить к блоку ПРИНЯТИЕ РЕШЕНИЯ опцию «С вложением»: пользователь может приложить файл к ответу. Это покроет сценарий «отправить документ в ответ».
3. **Далее** — новый блок «ЗАПРОС ДОКУМЕНТА»:
   - Настройки: кому запрос, описание, дедлайн.
   - При наступлении — уведомление с кнопкой «Приложить документ» / «Подтвердить получение».
   - После загрузки/подтверждения — процесс идёт дальше.
4. **Хранилище:** общая таблица `bp_instance_documents` (instance_id, node_id, uploaded_by, file_path, doc_type, created_at).
5. **UI:** в карточке экземпляра БП — вкладка «Документы» со списком загруженных файлов.

### 5.5. База знаний (отдельная задача на будущее)

- Компонент «База знаний» — справочник артикулов/наименований с характеристиками.
- При наборе в тексте (например, в ответе или в задаче) — автоподсказка по артикулам, вставка характеристик.
- Не входит в текущий план, но архитектурно лучше держать БЗ отдельно и подключать к БП через API.

### 5.6. Шаблоны документов

- Новый сервис/модуль «Шаблоны документов»: шаблон (HTML/DOCX) с плейсхолдерами `{{variable}}`.
- Блок БП «Создать документ по шаблону»:
  - Выбор шаблона.
  - Маппинг переменных (из context процесса, задачи, инициатора).
  - Результат — сгенерированный файл сохраняется в `bp_instance_documents` и/или отправляется участникам.

## Блок «РАЗВИЛКА-СЛИЯНИЕ» (рекомендация)

### Идея

Один блок объединяет **слияние** (ожидание от нескольких входящих) и **развилку** (выбор исходящей ветки по совокупности условий). Отдельная Развилка после него не нужна.

- **Входы:** несколько входящих стрелок от блоков «Создать задачу», «Назначить задачу», «Принятие решения» и т.д.
- **Выходы:** несколько исходящих веток; для каждой ветки задаётся **одна совокупность условий** по входящим источникам.
- В зависимости от того, **сколько** в блок входит узлов (задачи + решения), столько **источников** участвует в условиях. Минимум **одна** совокупность (одна исходящая ветка) должна быть задана; можно задать **несколько** вариантов совокупности для разных веток.

### Условия по входящим

Для каждой **исходящей** ветки задаётся комбинация:

- По каждому **входящему** источнику (задача 1, задача 2, принятие решения и т.д.):
  - либо **конкретное условие** (статус задачи = «Выполнено», кнопка = «Принять» / «Отклонить»),
  - либо **«Неважно»** — значение этого входа не проверяется для данной ветки.

Примеры:

- Ветка 1: задача 1 = Выполнено, задача 2 = Выполнено, решение = Ок.
- Ветка 2: задача 1 = Выполнено, задача 2 = Выполнено, решение = Отмена.
- Ветка 3 (иначе): можно задать «Иначе» или ещё одну совокупность с «Неважно» где нужно.

Таким образом блок сам и **ждёт** выполнения всех нужных входящих, и **выбирает** ветку по выбранной совокупности — передача в отдельный блок Развилка не требуется.

### Спецификация блока «Развилка-Слияние»

| Элемент | Описание |
|--------|-----------|
| **Тип узла** | `gateway_join` (или расширение текущего `gateway` с режимом «слияние») |
| **Входящие** | Определяются по схеме: все рёбра с `target = id` этого узла. Источники — узлы типов `create_task`, `assign_task`, `decision`. |
| **Настройки входящих** | Для каждого входящего (по `source` узла): тип источника (задача / принятие решения), при необходимости привязка к задаче (если несколько блоков задач). |
| **Исходящие** | Как у обычной Развилки: несколько стрелок. |
| **Условие ветки** | Для каждой исходящей стрелки — **одна совокупность**: по каждому входящему источнику — значение (статус / кнопка) или «Неважно». |
| **Порядок проверки** | После того как все входящие «сигнализировали» (есть статусы задач и результат решения), проверяются совокупности исходящих веток по порядку; первая подходящая задаёт следующий узел. При отсутствии совпадения — ветка «Иначе», если задана. |

### Логика выполнения

1. Процесс попадает в «Развилка-Слияние» по событию (обновление задачи / ответ по решению). Состояние «какие входящие уже имеют результат» хранится в контексте (например, `join_signals` или текущие данные по задачам и `last_decision`).
2. Когда **все** входящие источники имеют актуальное значение (обе задачи в каком-то статусе, решение нажато) — проверяем совокупности исходящих веток.
3. Выбирается первая исходящая ветка, чья совокупность совпала (для источников без «Неважно» — точное совпадение; «Неважно» — не проверяем).
4. Переход по выбранной стрелке; при необходимости — ветка «Иначе».

### Реализация (кратко)

- **Клиент:** новый тип блока «Развилка-Слияние» или режим у Развилки «несколько входящих (слияние)». UI: список входящих источников (авто по схеме); для каждой исходящей ветки — таблица/форма «источник 1 → значение или Неважно», «источник 2 → …», и т.д.
- **Сервер:** обработчик узла при событии (task_updated, respond-decision) проверяет, ведёт ли ребро к узлу «Развилка-Слияние»; обновляет состояние входящих; при «все готовы» вычисляет совокупность и возвращает `nextNodeId`.
- **БД:** при необходимости таблица ожидания (например, `bp_gateway_join_waiting`) для персистентности между событиями.
