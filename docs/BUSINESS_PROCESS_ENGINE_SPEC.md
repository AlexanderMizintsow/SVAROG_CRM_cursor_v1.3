# Движок бизнес-процессов SVAROG CRM — Техническое задание (теоретический этап)

## 1. Цель и границы

### 1.1 Цель
Создать в приложении SVAROG CRM компонент **«Бизнес-процессы»**, позволяющий:
- **Запускать** готовые бизнес-процессы от имени пользователя.
- **Создавать и редактировать** схемы бизнес-процессов в виде цепочки блоков с настраиваемыми действиями и условиями.
- В перспективе — собирать **аналитику** по исполнению процессов (время на этапах, узкие места, количество обращений).

### 1.2 Связь с существующим функционалом
- **Менеджер задач** — основной потребитель: создание задач по шаблонам, назначение исполнителей/утверждающих/наблюдателей, статусы, дедлайны.
- **Пользователи и отделы** — выбор инициатора, исполнителей, получателей уведомлений (по пользователю, отделу, роли).
- **Уведомления** — внутри приложения (Socket.io) и в Telegram (tg-bot-server, `telegramm_registrations_chat`).
- **Шаблоны задач** — расширяемая система шаблонов для блока «Создать задачу» (хранение и выбор готовых пресетов).

---

## 2. Структура компонента «Бизнес-процессы»

### 2.1 Две вкладки

| Вкладка | Назначение |
|--------|------------|
| **Готовые процессы** | Список сохранённых бизнес-процессов. Для каждого: название, описание, кнопка «Запустить». Запуск от имени текущего пользователя (или выбранного инициатора, если процесс это допускает). |
| **Конструктор** | Визуальный редактор схемы: палитра блоков слева, холст по центру, свойства выбранного блока справа. Сохранение процесса как черновик или готовый к запуску. |

### 2.2 Навигация и права
- Раздел «Бизнес-процессы» в меню (рядом с «Менеджер задач» или внутри CRM).
- Права: просмотр списка, запуск, создание/редактирование схем — через существующую систему `permissions` и ролей.

---

## 3. Визуализация и конструктор схемы

### 3.1 Принцип
- **Блоки** (узлы) соединяются **стрелками** (рёбрами). Каждый блок имеет тип и набор **настроек** (свойства).
- Движок при запуске процесса проходит схему от **Старта** по стрелкам, выполняя действия блоков и выбирая следующую ветку по условиям в блоках **Развилка**.

### 3.2 Палитра инструментов (левая панель)
Отдельный компонент — **«Инструменты бизнес-процесса»**. Список типов блоков с иконками и кратким описанием. Перетаскивание на холст или клик «добавить» с последующим размещением.

**Рекомендуемые типы блоков:**

| Тип блока | Иконка/цвет | Назначение |
|-----------|-------------|------------|
| **Старт** | Зелёный круг | Точка входа. Один на процесс. Настройки: кто инициатор. |
| **Конец** | Красный/серый круг | Завершение процесса (одна или несколько точек выхода). |
| **Действие: Создать задачу** | Прямоугольник (задача) | Создание задачи в Менеджере задач по шаблону с предустановками. |
| **Действие: Назначить задачу** | Прямоугольник (люди) | Назначение уже созданной задачи исполнителю/отделу/роли. |
| **Действие: Уведомление** | Прямоугольник (колокольчик) | Отправка сообщения: в приложение и/или в Telegram. |
| **Развилка** | Ромб | Условие: куда идти дальше (например, задача выполнена / не выполнена / просрочена). |
| **Таймер/Ожидание** | Часы | Ожидание N часов/дней или до наступления даты, затем переход по стрелке. |
| **Подпроцесс** | Двойной прямоугольник | Вызов другого бизнес-процесса как подпроцесса (опционально, фаза 2). |

Расширяемость: новые типы блоков регистрируются в конфиге (массив типов + компонент настроек + обработчик на бэкенде), без жёсткого перечисления в коде.

### 3.3 Холст
- Схематичное отображение блоков и стрелок (SVG или Canvas, либо библиотека типа React Flow / аналоги без лишних зависимостей — по архитектуре проекта).
- Перетаскивание блоков, рисование связей «от выхода к входу».
- Выделение блока — открытие панели свойств справа.
- Валидация: ровно один Старт; от Старта достижимы все блоки; у развилок — явные условия на каждое исходящее ребро.

### 3.4 Стрелки и условия
- Обычная стрелка: «после выполнения блока перейти к следующему».
- У блока **Развилка** несколько исходящих стрелок; у каждой — **условие** (например: «задача выполнена», «срок пропущен», «любой исход»). Условия задаются в настройках развилки и привязываются к контексту процесса (например, к последней созданной задаче).

## 4. Блоки и их настройки (подключаемые возможности)

### 4.1 Блок «Старт»
- **Инициатор процесса**
  - Вариант: **Текущий пользователь** — кто нажал «Запустить» (рекомендуется по умолчанию).
  - Вариант: **Конкретный пользователь** — выбор из списка пользователей (из API `getUsers`).
  - Вариант: **Роль** — любой пользователь с выбранной ролью (при запуске всё равно подставляется текущий, если он подходит под роль; иначе — предупреждение).
- Дополнительно: название процесса для отображения в списке запусков, описание (необязательно).

### 4.2 Блок «Создать задачу»
Использует возможности Менеджера задач и будущие шаблоны задач.

- **Шаблон задачи**  
  Выбор из списка сохранённых шаблонов (шаблоны хранить в БД: название, описание, приоритет, теги по умолчанию, дедлайн относительно старта процесса и т.д.). Если шаблонов ещё нет — форма как в AddModal: название, описание, приоритет, теги, дедлайн.
- **Автор задачи (created_by)**  
  Инициатор процесса или конкретный пользователь из настроек.
- **Исполнители**  
  Один или несколько: выбор пользователей, или «из предыдущего блока» (например, из результата блока «Назначить»), или по роли/отделу (руководитель отдела, все из отдела X).
- **Утверждающие (approvers)**  
  Аналогично: список пользователей или правило (роль/отдел).
- **Наблюдатели (viewers)**  
  То же.
- **Дедлайн**  
  Фиксированная дата/время или смещение от момента создания задачи (например, +3 дня).
- **Связь с процессом**  
  Созданная задача привязывается к экземпляру процесса (process_instance_id, task_id), чтобы следующие блоки (развилки, уведомления) могли ссылаться на «последнюю созданную задачу» или «задачу этого шага».

Результат блока для следующих шагов: `task_id` (и при необходимости `task` объект).

### 4.3 Блок «Назначить задачу»
- **Задача**  
  Выбор: «задача, созданная в блоке X» (по id блока на схеме) или конкретная задача по ID (редко).
- **Кому назначить**  
  Пользователь(и), отдел, роль. При отделе/роли — назначение первому подходящему или всем (настраиваемо).
- Опционально: добавить утверждающих/наблюдателей.

Использует существующие API: `assignment/add`, при необходимости `replaceTaskAssignment`.

### 4.4 Блок «Уведомление»
- **Получатели**  
  Конкретные пользователи, отдел, роль, или «исполнитель задачи X», «автор задачи X», «инициатор процесса».
- **Канал**
  - В приложении (Socket.io + запись в таблицу уведомлений/reminders для панели уведомлений в Менеджере задач).
  - В Telegram — если у пользователя есть `chat_id` в `telegramm_registrations_chat`.
  - Оба канала с галочками.
- **Текст сообщения**  
  Текстовое поле + возможность подстановок: `{инициатор}`, `{исполнитель}`, `{название_задачи}`, `{дедлайн}`, `{статус}` и т.д.
- **Приоритет уведомления**  
  По аналогии с `reminders.priority_notifications` (low, normal, high) для отображения в интерфейсе.

### 4.5 Блок «Развилка»
Определяет следующую ветку по условию.

- **Условие привязано к**  
  Задаче, созданной в блоке с id X (или «последняя созданная в процессе задача»).
- **Варианты условий (исходящие стрелки)**  
  - Задача **выполнена** (статус done и is_completed = true).  
  - Задача **не выполнена** (статус не done или не подтверждена).  
  - **Просрочена** (текущая дата > deadline и задача не выполнена).  
  - **В срок** (выполнена до deadline).  
  - **Ожидание одобрения** (есть утверждающие и не все утвердили).  
  - **Любой исход** / иначе (default ветка).  
- На каждую исходящую стрелку — ровно одно условие. Порядок проверки: сначала конкретные (выполнена, просрочена), затем «иначе».

Реализация: движок после выполнения блока «Создать задачу» или «Назначить» сохраняет в контексте процесса `last_task_id`. В блоке «Развилка» по этому id запрашивается статус/дедлайн и выбирается следующая ветка.

### 4.6 Блок «Таймер / Ожидание»
- **Тип ожидания**  
  - Интервал: N минут/часов/дней от момента входа в блок.  
  - До даты/времени (фиксированная или вычисленная, например «конец рабочего дня»).  
- **Выход**  
  Одна стрелка — переход после срабатывания таймера. Реализация: фоновый воркер (cron или очередь) проверяет активные экземпляры процессов, находящиеся на блоке «Таймер», и переводит их дальше по времени.

### 4.7 Блок «Конец»
- Никаких действий. Состояние экземпляра процесса: «завершён».
- Можно несколько блоков «Конец» для разных веток (успех, отмена, эскалация и т.д.) с подписями для аналитики.

## 5. Данные и хранение

### 5.1 Модель данных (предлагаемая)

- **business_processes**  
  id, name, description, scheme (JSON: узлы и рёбра), is_draft, created_at, updated_at, created_by.  
  - `scheme`: список узлов `{ id, type, position, settings }` и список рёбер `{ fromNode, toNode, condition? }`.

- **business_process_instances**  
  id, process_id, started_at, finished_at, initiator_id, current_node_id, status (running, waiting_timer, completed, failed), context (JSONB).  
  - `context`: переменные процесса: last_created_task_id, block_outputs { blockId: { task_id, ... } }, таймеры и т.д.

- **task_templates** (если ещё не существует)  
  id, name, description (HTML/текст), priority_default, tags_default, deadline_offset_days, created_at, created_by.  
  Для блока «Создать задачу» — выбор шаблона и переопределение полей при необходимости.

- **business_process_node_execution_log** (для аналитики)  
  id, instance_id, node_id, entered_at, exited_at, outcome (success, condition_met, error).  
  Позволяет считать время на каждом этапе и строить отчёты.

### 5.2 Связь с задачами
- В `tasks` можно добавить поле `business_process_instance_id` (или отдельная таблица `task_process_links`: task_id, process_instance_id, block_id), чтобы при изменении статуса задачи движок мог обновить состояние процесса (например, развилка «задача выполнена»).

## 6. Запуск процесса и движок исполнения

### 6.1 Запуск
1. Пользователь в списке «Готовые процессы» нажимает «Запустить» (опционально выбирает себя или другого инициатора, если процесс это разрешает).
2. Создаётся запись в `business_process_instances`: status = running, current_node_id = id узла «Старт», context = { initiator_id }.
3. Серверный движок входит в цикл: обрабатывает текущий узел, выполняет действие (если есть), пишет лог в `business_process_node_execution_log`, определяет следующий узел по стрелкам и условиям, обновляет `current_node_id` и `context`. Если следующий блок — «Таймер», переводит в status = waiting_timer и выходит; воркер по расписанию потом переведёт на следующий узел.

### 6.2 Обработка событий от Менеджера задач
- При смене статуса задачи на «выполнена» / подтверждении (updateTaskStatus, updateTaskAccept) сервер проверяет, есть ли экземпляры процессов, ожидающие в блоке «Развилка» по этой задаче. Если да — пересчитывает условие и переводит процесс на следующую ветку (и при необходимости создаёт задачи/уведомления в следующих блоках).

### 6.3 Ошибки
- При ошибке создания задачи или отправки уведомления: запись в лог, статус узла outcome = error. Варианты: перевести процесс в status = failed или в специальный узел «Обработка ошибки» (опционально).

## 7. Аналитика (перспектива)

Для последующей реализации заложить:

- **Время на этапе**  
  По `business_process_node_execution_log`: разница между entered_at и exited_at по node_id и instance_id.
- **Средняя длительность процесса**  
  По instance: finished_at - started_at.
- **Узкие места**  
  Блоки с наибольшим средним временем и наибольшим количеством проходов.
- **Частые ветки**  
  Какие условия развилок срабатывают чаще (выполнено в срок / просрочено / не выполнено).
- **Количество запусков**  
  По процессам и по пользователям/отделам.

Рекомендуется при создании схемы и логов использовать стабильные id узлов и имён блоков, чтобы отчёты можно было строить без привязки к версии схемы.

## 8. Интеграции

### 8.1 Менеджер задач
- Создание задачи: вызов существующего API `POST /api/tasks/create` и `assignment/add`, `approval/add`, `visibility/add`.
- Шаблоны: либо новая сущность `task_templates` с API, либо расширение текущего `templateOptions` и хранение в БД.
- Получение статуса задачи: `GET /api/tasks/:taskId` (status, is_completed, deadline).

### 8.2 Пользователи и отделы
- Список пользователей: `GET /api/users`.
- Отделы и руководители: существующие API отделов (getDepartments и т.д.).
- Роли: для выбора «исполнитель по роли» — данные из ролей пользователей.

### 8.3 Уведомления
- В приложении: существующий механизм Socket.io (emit событий) и при необходимости запись в `reminders` для панели уведомлений в Менеджере задач.
- Telegram: через tg-bot-server (отправка сообщения по user_id → chat_id из `telegramm_registrations_chat`). Учесть, что не у всех пользователей может быть привязан Telegram.

## 9. Расширяемость

- **Новые типы блоков**  
  Регистрация в конфиге: тип, метаданные для палитры, компонент настроек (React), обработчик на бэкенде (функция nodeHandler). При добавлении нового типа не менять ядро движка, только добавлять запись и маршрут.
- **Новые условия в развилках**  
  Словарь условий (например, «задача возвращена на доработку») с функцией проверки на бэкенде.
- **Подстановки в уведомлениях**  
  Словарь переменных процесса (инициатор, задача, дедлайн, кастомные поля из context) для использования в тексте сообщений и шаблонах.

---

## 10. Этапы реализации (рекомендуемый порядок)

1. **Модель данных и API**  
   Таблицы business_processes, business_process_instances, при необходимости task_templates и task_process_links. CRUD для процессов и шаблонов.
2. **Компонент «Бизнес-процессы»**  
   Две вкладки: список процессов + кнопка «Запустить» (пока без реального движка — заглушка).
3. **Конструктор схемы**  
   Палитра блоков (Старт, Конец, Создать задачу, Развилка, Уведомление), холст, сохранение scheme в JSON.
4. **Движок исполнения (бэкенд)**  
   Один поток: Старт → следующий узел по стрелке; блок «Создать задачу» (с шаблонами); блок «Уведомление» (in-app + TG); блок «Развилка» по статусу задачи.
5. **Интеграция с задачами**  
   Привязка созданных задач к process_instance; обработка смены статуса задачи для развилок.
6. **Блоки «Назначить задачу» и «Таймер»**  
   Расширение движка и палитры.
7. **Аналитика**  
   Логирование входа/выхода из узлов, отчёты по времени и количеству запусков.

## 11. Краткое резюме возможностей

| Что | Как |
|-----|-----|
| Инициатор | Текущий пользователь или выбранный заранее (Старт). |
| Создание задачи | Блок по шаблону с настройкой автора, исполнителей, утверждающих, наблюдателей, дедлайна. |
| Назначение | Блок «Назначить задачу» — кому передать (пользователь/отдел/роль). |
| Уведомления | В приложение и/или в Telegram, с подстановками и выбором получателей. |
| Условия | Развилка по выполнению/просрочке/ожиданию одобрения задачи. |
| Таймеры | Ожидание N времени или до даты, затем переход. |
| Аналитика | Лог прохода по узлам → время на этапах, узкие места, количество запусков. |
| Расширяемость | Новые типы блоков и условий через конфиг и обработчики без переписывания ядра. |

Документ подготовлен как теоретическая основа для последующей реализации движка бизнес-процессов в SVAROG CRM.
